## D22

**Reproduced the shared staging-path race in memory with both writer bodies.**

1. Writer A calls `compress_als(valid_lines, out)` for `Sections V9.als`. It writes and validates `Sections V9.als.partial`, then pauses before `replace`.
2. Writer B calls `compress_als(["<not-an-als>\n"], out)`. It overwrites the same partial, closes it, and pauses before validation.
3. A resumes and renames B's malformed gzip payload onto `Sections V9.als`. B's later failure and cleanup leave that published file in place. An existing valid output can be overwritten this way.

In a single call, both writers attempt cleanup in `finally` even when the validator raises an unexpected `RuntimeError`. The exception propagates and the prior output stays intact. **Cleanup is best effort.** If the partial is held open without delete sharing on Windows, `unlink` can raise `PermissionError`. Both helpers swallow that error, leaving the partial behind. A `PermissionError` from the final rename is wrapped as `ValueError`, and the prior output stays intact. `apply_automation.compress_als` delegates to `apply_loops`.

`generate_session` passes both job gates to `als_generator.compress_als`, which runs them on the partial before renaming. **Phase 3 has a separate post-publication failure path.** Call `apply_automation.main` with otherwise valid inputs and a supplied MixPlan whose transitions disagree with the result. It publishes the ALS, may update the arrangement report, then calls `reconcile`. A reconciliation failure leaves a structurally validated ALS that failed the job's hard gate (`apply_automation.py:1634, 1643, 1672`).
