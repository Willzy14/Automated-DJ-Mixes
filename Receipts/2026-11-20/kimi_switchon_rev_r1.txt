  **3. Fills as cue points**

  **4. Hints window**

  The window is anchored at the right end in both modes: `pre = outro_start if outro_start is not None else end_sec; window_start = pre - 32 * sec_per_bar` (diff 1663-1665, unchanged lines). Groove collects `f.end_sec` in `[window_start, pre]` (inclusive, and `< end_sec`), defaulting to `outro_start` (diff 1668-1671). For a track with no outro label: raw `outro_start` is None, so with no eligible fill ends `last_bass_drop` is None; the unchanged fallback block then synthesizes `outro_start = max(first_drop + sec_per_bar, end_sec - 32 * sec_per_bar)` (verified on main, stem_detector.py:1623-1624) and the new groove fallback sets `last_bass_drop = outro_start`, clamped to `end_sec`. So a real hint is always emitted — this matches the builder's two fallback-hint tracks (Call 911, MASON Collective). Is a skipped check a silent pass? Yes. The gate only runs the last-bass-vs-outro check `if last_bass is not None and outro is not None` (diff 775-779), where `outro` comes from the extracted clips; a no-outro track skips the check entirely, and missing hint fields are skipped by `continue` (diff 767-769). So for exactly the tracks where the hint is most likely to be a synthetic guess, nothing ever validates it. Note the asymmetry this creates: groove fallback lands at end - 32 bars (window edge, defensible); the legacy fallback lands at synthetic_outro - 16 = end - 48 bars, i.e. outside its own 32-bar window — pre-existing, unchanged, but worth knowing before trusting legacy comparisons. Also deliberate but undocumented: groove eligibility uses `<= pre` (a fill ending exactly at the outro start counts) while legacy uses `< pre`.
