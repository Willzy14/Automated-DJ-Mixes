2. THE VERS CHANGE IN resolve_masters.py (the brief's open question)
====================================================================

VERS (resolve_masters.py:41) is used in six places, none of which is `ver()`:

    46/48  bare()   - strips VERS tokens (after DECO strips the decoration groups)
    54 vonly()  - "has a version token AND is decoration-only"
    64     vt - "the searched title is made only of version words"
    74     tk      - only relevant when vt is true
    75     vo      - dc AND has a VERS token
    97     hd      - held-for-NOTE test

`ver()` (21-26) does NOT use VERS. It has its own literals: `sw v\d+`, `amended v\d+`, `amended`, and the literal substring '24 bit'. So the VERS change cannot change any version score directly. It changes which names are "titled" (bare()), which changes `same`, `one`, `vo`, `hd`, and therefore promotion and NOTE behaviour.

Your specific question: a folder holding both a "16 Bit MASTER" and a "24 Bit MASTER" of the same track.

    bare("Artist - Title 16 Bit MASTER.wav", "artist")
      before: "artist title 16 bit master" -> VERS(old) eats "master" -> s[6:] = "title 16 bit" -> bare = "title 16 bit"  != title -> NOT a titled file
      after:  VERS(new) also eats "16 bit" -> s[6:] = "title" -> bare = "title" == title -> IS a titled file
    bare("Artist - Title 24 Bit MASTER.wav", "artist") = "title" both before and after (24 bit was already a token).

Ranking of the two candidates (the sort key is ((not junk, named or up, must, nm-in-kn), mx, ver(f), want_t, mt, fp), and out.sort(reverse=True)):

    named is True for both, mx = mix(f) = 0 for both, so the tie-break is ver(f):
      ver("...16 bit master") = 0    (no sw, no amended, and '24 bit' not in the name)
      ver("...24 bit master") = 5    (the legacy +5 for '24 bit' in the no-SW branch)
    -> the 24 Bit file wins, BEFORE and AFTER the change. The VERS change does not move this decision.

So: 24 Bit wins before and after, and rule 5 does not speak about bit depth at all, so nothing is violated. But the change does create two real inconsistencies worth your decision (details in FOUND UNASKED):
  - 32 Bit MASTER is now a recognised delivery label yet still scores ver() = 0, so a 24 Bit file still beats a 32 Bit file. 24 > 32 is not defensible on quality grounds.
  - 16 Bit vs 32 Bit (both ver() = 0) is decided by mtime and then by the path string, i.e. by nothing the rules mention. Silently non-deterministic from the owner's point of view.

The change is not purely additive, though. It can flip the resolver's own answer in a folder that contains a bit-depth delivery plus a version-only delivery:

    Folder "Artist - Title [Label] Project":
      "Artist - Title 16 Bit MASTER.wav"   (titled after the change, untitled before)
      "MASTER AMENDED V2.wav" (version-only)
    before: same = {} -> one = False -> the version-only file is HELD (NOTE), answer = the 16 Bit file
    after:  same = {the 16 Bit file} -> one = True -> the version-only file is PROMOTED, answer = "MASTER AMENDED V2.wav"

The new answer is the one the resolver's own documented rule wants (the folder is exactly "artist - title", every live file is a titled file or a version-only file, at least one titled file exists, and rule 5 says AMENDED V2 is newer than MASTER). So the flip is an improvement, not a regression, but it is a silent behaviour change to the standalone tool for libraries that already contain "16 bit"/"32 bit" names.

Bottom line for point 2: adding 16 and 32 to VERS changes no ranking or promotion decision for names that do not contain those tokens. For names that do contain them, it changes the "titled file" classification and can promote a version-only delivery that was previously held. The 16-vs-24 winner is unchanged (24 won before and wins now, on the legacy '24 bit' +5 that the brief says was not changed). The bit-depth ordering is now undefined between 16/32 and inconsistent between 24 and 32, which rule 5 does not cover and which I therefore raise in FOUND UNASKED rather than in the verdict.

3. FALSE NONE (real-world names that get refused)
====================================================================

The builder's title-only rule is much stricter than the resolver's own `named` test. scan() matches a candidate when the title appears as whole words in the file name (kn = norm(stem(f)), unstripped); master_name_matches requires the file name to be EXACTLY "<artist> <title>" or "<title>" plus nothing but version tokens (or an allowed mix word plus version tokens). Result: files the standalone resolver would print can come back NONE from --resolve. Cases, all fail-safe (NONE, never a wrong MASTER):

  - Track number without a separator: "12 Title.wav". strip_num (resolve_masters.py:36) only removes "\d{1,3} + separator" or zero-padded "0\d ". "12 Title" is neither -> the name stays "12 title" -> the base "title" does not match -> REFUSED. The resolver's `named` test uses the unstripped kn, so it WOULD answer this file. Zero-padded "01 Title.wav" and "01 - Title.wav" are fine (verified: strip_num removes "02 " via the 0\d alternative). Your library's fixtures are zero-padded, so the practical risk is low, but the divergence is real.
  - A label or catalogue tag in the FILE name: "Better When [Defected].wav" -> norm "better when defected" -> tail "defected" -> not a version token -> REFUSED. Same for "(2024 Remaster)" -> tail "2024 remaster" -> refused. The resolver's bare() also keeps those, but its `named` test still finds the file, so again the two tools disagree.
  - "24 Bit  MASTER" (double space): fine. norm collapses runs of non-alphanumerics to one space.
  - Apostrophes: "Don't Stop" -> "don t stop" on both sides -> fine, as long as the DB and the file agree. "Dont Stop" in the file vs "Don't Stop" in the DB -> mismatch -> refused.
  - Accents: norm strips non-ASCII rather than transliterating, so "Cafe" -> "cafe" but "Café" -> "caf". If both the DB row and the file name carry the accent they still match ("caf" == "caf"), so this only bites when the two sides differ. Pre-existing in the resolver (same norm), so not new here.
  - "feat." forms: DB "A feat. C" -> "a feat c"; the folder "A & C" -> "a c" -> the title-only branch refuses. A file named "A feat. C - Title.wav" still matches through the first branch.
  - Mix names that the DB spells differently from the file: a row with remixer="Bob" and mix_name="Extended Mix" builds version "bob extended mix" (resolve_pick:165 prepends the remixer when the remixer name is not already in the mix name), so the file must literally contain "bob extended mix". A file "Title (Extended Mix) SW V1.wav" -> REFUSED -> NONE. Same for remixer="Bob" + mix_name="Original Mix" -> version "bob original mix". Conservative (never a wrong answer) but a plausible false NONE if the credits table has rows with both fields populated.

Your specific uncertainty ("will exact artist matching return NONE for most collaborations?"): no, and here is why. The folder equality test only guards the SECOND branch of master_matches. The FIRST branch ("<artist> <title>" as the file name prefix) never looks at the folder. And scan() itself requires `a in n` on the NORMED folder name, so a DB artist "A & B" only scans folders whose name contains "a b" at all. The refusal is therefore narrow: it bites only for title-only files (files named "Title (Mix) SW Vn.wav" with no artist prefix) sitting in a folder whose artist spelling differs from the DB spelling ("&" vs "and", "feat." vs "&"). Files that carry the artist prefix still resolve.

1. The original row and the "Extended Mix" row can both print the same MASTER.
