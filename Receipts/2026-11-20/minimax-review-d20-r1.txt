## 2. Breaking it

### F1 (medium, real): the no-cache fallback writes a `kick_model: false` json that the next run silently trusts. The original hint bug becomes permanent.

The fallback calls `detect(w, args.project, make_viz=False, kick_model=args.kick_model, ...)`. `write_json` is **not passed**, so it defaults to `True` (line 834). `detect()` therefore writes `SECTIONS_STEM_<track>.json` with `"analysis": {"kick_model": false}` (line 1265-1273).

Sequence:

1. Project has a good Phase 1a json? No. Say the json is missing, or Phase 1a was never run for that track, or the json was deleted.
2. Run `python Source/stem_detector.py <project> --write-hints`. No cache -> `[WARN] no cached analysis` -> `[WARN] this detect runs WITHOUT the kick detector` -> `detect()` runs with the kick model off and **writes** a `kick_model: false` json to `_Stem Analysis/`.
3. Run `--write-hints` again. The cache now exists and is well formed. The shape check passes. Output line is `  <track>: hints from the cached analysis (SECTIONS_STEM_<track>.json)`. **No warning of any kind.** The hints now come from a no-kick-model analysis.

So the bug this change fixes re-appears on the *second* run, silently, and it is self-perpetuating. Step 2 is the only place the user sees a warning; step 3 is the run whose output actually lands in `Hints/track_hints.json`, and it looks clean.

This is exactly the failure the brief describes as the thing to fix ("hints still come from a no-kick-model analysis without a visible warning"), and the fix does not close it for the no-cache case.

Two independent ways to make this bite:

- **F1a**: the fallback's `detect()` should not write the json at all (`write_json=False`). It is a hints-only step; the analysis it produced is explicitly the weaker one the change exists to avoid propagating. Writing it destroys the Phase 1a json's slot for any *future* Phase 1a run that does not pass `kick_model=True` (see F3).
- **F1b**: even without F1a, the trust check should refuse (or loudly warn about) a cached json whose `analysis.kick_model` is false, because that is precisely the json the pipeline says not to trust.

Note the asymmetry: the guard in D protects a *kick-on* json from being overwritten by a *kick-off* run. Nothing protects a *kick-off* json from being trusted for hints. The two halves of the fix are not symmetric, and the missing half is the one that produces wrong hints.

### F2 (medium): `hints_from_stem_result` raises `ZeroDivisionError` on a cached json with `bpm: 0`, which is uncaught, and kills the whole `--write-hints` run with a traceback and no hints file.

`hints_from_stem_result` does `sec_per_bar = 4 * 60.0 / res["bpm"]` (line 1444). With `"bpm": 0` that is `ZeroDivisionError` (Python raises this for float division by zero). The except tuple at line 1516 is `(KeyError, IndexError, TypeError, ValueError, json.JSONDecodeError)`. `ZeroDivisionError` derives from `ArithmeticError`, not from any of those. `json.JSONDecodeError` is a subclass of `ValueError`, so listing it is redundant, but harmless.

Consequence: the exception escapes the try, escapes the for loop, and aborts `main()` before `hints_dir.mkdir(...)` / `out.write_text(...)`. The user gets a Python traceback and **no** `Hints/track_hints.json` at all, even for the tracks that were fine. A stale `track_hints.json` from a previous run is left in place, so the failure can masquerade as success downstream.

This is reachable from a truncated or hand-edited json, or from a json written by a different tool with a null/zero bpm. The fix is to add `ArithmeticError` to the except tuple (or `Exception`).

### F3 (medium): the guard blocks the write but `detect()` still returns and the caller still uses the result, so the "no overwrite" protection is a partial protection for the file but not for the caller.

In the `--write-hints` fallback, `detect()` writes the json only if `_may_overwrite_sections_json` returns True. But `detect()` always returns `result` regardless of whether the write happened. So on a refused write:

- the on-disk json stays the good kick-on one (correct), but
- the hints are computed from the fresh no-kick analysis (wrong), with only `[WARN] this detect runs WITHOUT the kick detector` as the signal.

In the `--write-hints` flow this specific combination is hard to reach (if the cache was well formed we never call detect; if it was malformed it cannot have a kick-on `analysis` key). But it is reachable for `reverify_fast.py` / `reverify_sections.py`, which the brief already flags as known. I am not re-raising that. The point I am adding is that **`detect()` has no way to tell its caller that the write was refused**. `detect()` returns a result whose `analysis.kick_model` says `false`, while the file on disk says `true`. Any caller that assumes "the json on disk is what detect just produced" is now wrong. A `written` flag on the result, or a distinct return, would let callers notice.

### F4 (low): the guard's own warning cannot fire from `--write-hints`, so the one line that explains the situation is dead code in the documented workflow.

`_may_overwrite_sections_json` prints `[WARN] {path.name} was written WITH the kick model; this run has it off, so the file was NOT overwritten` only when `kick_model_on` is False and the existing file records `kick_model: true`. In `--write-hints`, that combination requires a cache that parses AND records `kick_model: true` AND still fails the shape check. A json that records `kick_model: true` was written by `detect()` and always has the shape `hints_from_stem_result` wants, so the shape check will not fail on it. **The branch is effectively unreachable via `--write-hints`.** It is reachable via `reverify_*` (already known).

This matters for the brief's question 1 ("the fallback in B/E followed by the guard in D"): the answer is that D never fires in the `--write-hints` path, so D does not help F1 at all. D protects the file; nothing protects the hints.

### F5 (low): a legacy json (no `analysis` key) is trusted for hints with no warning, even though it may be a stale kick-off analysis from the old `--write-hints` step.

This is the "first run after this change on a project whose json files are legacy" case the brief asks about. The legacy json was written by the *old* `--write-hints` step, which ran `detect()` without the kick model. Its sections may disagree with the Ableton set that was built from the Phase 1a analysis that it overwrote. The new code reads it, the shape check passes, and it prints `hints from the cached analysis` with no warning.

The `analysis` key cannot distinguish these, because the legacy json has no key at all. The code treats "legacy" as fine for the overwrite guard (D, defensible: a legacy file is at least as good as a fresh kick-off run) but also treats "legacy" as fine for the hints (not defensible: for hints, a legacy file is of unknown provenance and the old pipeline wrote it from a weaker analysis).

At minimum the no-`analysis`-key case deserves a distinct line such as `[warn] cached json has no analysis.kick_model record (legacy); hints may not match the pipeline run`. That would have made the first post-change run on an existing project self-diagnosing instead of silent.

### F6 (low): the shape check does not verify the cached json belongs to this track.

`hints_from_stem_result` never looks at `res["track"]`. The json does carry a `"track"` field (written at line 1266 as `wav.stem`), and `propose_arrangement.py:339` in the readers list is documented as reading the json's own `"track"` field, so the field is real and meaningful. A cached json whose `"track"` does not match `w.stem` (stale file left over from a renamed track, or a copy-paste of `_Stem Analysis` between projects) passes the shape check and is trusted. A one-line comparison `res.get("track") == w.stem` would close it.

### F7 (low): the shape check does not verify the cached json was produced by the current detector, so a stale json from an older detector version passes.

Nothing in the json records a detector version or the analysis parameters that shaped the sections (downbeat, `soft_intro_outro`, `width_cues`, `tier_a`, kick source). `signals.kick_presence_source` is the only provenance hint and it is not checked. A json produced by an older build of `stem_detector.py` (or by a build with different tunables such as `MIN_ENERGY_RUN_BARS`, `DROP_REL`, `OUTRO_CAP_BARS`) has exactly the shape the check wants and is trusted, so hints are derived from sections the current pipeline would not have produced. The `analysis` dict is the natural place for a version/params stamp.

### F8 (low): `analysis.kick_model` is `true` whenever a `kick_provider` was passed, regardless of whether the provider was actually used or whether it worked.

`kick_model_used = bool(kick_model or kick_provider is not None)`. Meanwhile the actual kick path in `detect()` is gated on `if kick_model or kick_provider is not None:` (line 923) and the provider call itself is `_model_kick_presence_per_beat(...)`. So the flag and the behaviour line up on the *attempt*.

The gap: if the provider raises, `detect()` propagates the exception and no json is written at all (so no stale-file corruption, and the caller sees the error). But if a provider is passed that returns an all-`False` readout, or a provider whose `presence_per_beat` yields a degenerate signal, `detect()` records `kick_model: true` and the sections are garbage, and the guard then **refuses to let anything overwrite that garbage**. A bad kick-on analysis is now permanent: no kick-off run can replace it, and the only escape is a fresh kick-on run. There is no "the model ran but produced nothing" signal, and `analysis` records only the flag, not the source string that already exists as `signals.kick_presence_source`. Recording the actual `kick_source` in `analysis` would at least make the condition visible to the reader and to the hint path.

### F9 (medium): `materialize_section_details.py` writes `SECTIONS_STEM_<name>.json` into a `refined_stem_dir` (line 198). If that writer does not carry the `analysis` key through, the refined json is treated as legacy by the guard.

I cannot see that file, so this is a flag, not a confirmed defect. What I can say from the grep line alone: `materialize_section_details.py:198` performs a `write_text(...)` of a `SECTIONS_STEM_<clean_name>.json`. If it constructs the dict from scratch rather than loading and re-emitting the detector's json, the `analysis` key will be missing, and the guard will treat that refined file as legacy (overwritable). That is probably harmless for the guard (the refined dir is not the pipeline's Phase 1a file) but it means the `analysis` key is not reliably propagated through the toolchain. Whoever writes json into that tree should preserve `analysis`, or the guard's notion of "kick-on file" is only valid for the one file `detect()` writes.

## 5. Windows cp1252 console safety

**All new print templates are plain ASCII.** I checked each one:

- `f"  {w.stem[:42]}: hints from the cached analysis ({cached.name})"` - ASCII literals.
- `f"  [warn] malformed cache {cached.name}: {type(exc).__name__}: {exc}; falling back to a fresh detect"` - ASCII literals; `{type(exc).__name__}` is an identifier; `{exc}` for `json.JSONDecodeError` is ASCII ("Expecting property name enclosed in double quotes: line 1 column 3 (char 2)"). For `UnicodeDecodeError` the message contains a `repr` of the offending bytes, which is ASCII-escaped.
- `f"  [WARN] no cached analysis for {w.stem[:42]} ({cached.name}); running detect"` - ASCII literals.
- `f"  [WARN] this detect runs WITHOUT the kick detector and may disagree with a pipeline run"` - ASCII literals.

## 6. Answering the brief's open question: should "no cache, kick model off" be a hard error?

**No, not as the primary fix, because it does not address the actual defect.**

Making it a hard error is defensible as a safety measure: with no cache and no kick model, the hints will be derived from a weaker analysis and the hints-vs-sections gate may fail, so refusing to write bad hints is arguably right. But it has real costs:

- It breaks the documented standalone workflow for any project that has not run Phase 1a with the kick model. Some users may legitimately want a hint-only pass.
- It is **not sufficient**, because the same weaker analysis reaches `Hints/track_hints.json` through a second, quieter route: F1, the second run against the `kick_model: false` json the fallback itself wrote. A hard error on the *no-cache* path would not stop that path at all, because on the second run there **is** a cache.
- It does not address F5 (legacy json with no `analysis` key, silently trusted) either.

My recommendation, in priority order:

1. **Stop the fallback from writing the json.** `detect(w, args.project, make_viz=False, write_json=False, ...)` in the `--write-hints` fallback. This is a one-word change and it kills F1 at the root: `--write-hints` becomes read-only with respect to `_Stem Analysis/`, which is the property the whole change is trying to establish. It also stops the fallback from clobbering a Phase 1a json in the legacy/no-`analysis` case (F5's file gets destroyed by the very step meant to read it). This is the highest-value correction.
2. **Refuse to silently trust a `kick_model: false` cache.** If the cached json records `kick_model: false`, either fall back to detect (with the kick model if available) or print a prominent warning that the hints are from a no-kick-model analysis. At minimum, warn.
3. **Warn on a cache with no `analysis` key** (legacy): `[warn] cached json has no analysis record (legacy); hints may not match the pipeline run`.
4. **Add `ArithmeticError` to the except tuple** so `bpm: 0` cannot crash the run (F2). One word.
5. **Cover the wiring**: a test that asserts `detect()` does not write when the guard refuses, and a test that asserts the fallback does not write the json. Since `detect()` needs audio, the practical route is to extract the write into a tiny helper (e.g. `_write_sections_json(path, result, kick_model_used)`) that both `detect()` and the tests can call.
6. Optional, cheap: compare `res.get("track") == w.stem` in the trust check (F6); stamp a detector version into `analysis` (F7); rename `analysis` to something less collision-prone.

F1 is the one I would call a must-fix: as written, the change makes the original bug *look* fixed on the second run of the very workflow the bug was found in.

## FOUND UNASKED

1. **`ZeroDivisionError` is not in the malformed-cache except tuple** (line 1516), so a cached json with `"bpm": 0` crashes the whole `--write-hints` run with an unhandled traceback. No hints file is written at all, and any stale `Hints/track_hints.json` from a previous run survives, so the failure looks like success downstream. Fix: add `ArithmeticError`. (F2)

2. **`--kick-model` is a silent no-op whenever a cache exists.** The cached branch never consults `args.kick_model`. If a `kick_model: false` json is cached, running `--write-hints --kick-model` still uses the cached kick-off json and never runs a kick-on detect. The two flags now interact in an undocumented way. This is also the natural place to implement fix #2 above: when `--kick-model` is passed and the cache is not kick-on, re-run detect with the model. (F1 / interaction)

3. **`hints_from_stem_result` is called twice on the cached path** (once as the shape check at line 1514, once to build the hints at line 1534). Harmless for correctness, but the shape check's *result* is thrown away. Returning the hints from the first call and reusing them would remove the duplication and make the "shape check" a real thing rather than a discarded smoke test.

4. **The `--write-hints` fallback writes to `_Stem Analysis/`, so the documented step is not read-only.** This is the root of F1 and is arguably a scope violation of the whole change: a step whose purpose is "write hints" should not be writing the pipeline's analysis cache. One-word fix: `write_json=False`.

5. **`json.JSONDecodeError` in the except tuple is redundant** (it is a subclass of `ValueError`). Harmless, but it suggests the author was not certain which exceptions `json.loads` raises, and it did not prompt checking the one that actually escapes (`ZeroDivisionError`).

6. **`prior.get("analysis") or {}` is defensive in a way that hides a bug class.** If a writer ever emits `"analysis": "kick-detector-v3"` (a string) or `"analysis": []`, the `or {}` fallback means `prior_kick` is False and the file is treated as legacy and overwritten, with no warning. A stricter check that distinguishes "key absent" from "key present but malformed" would let the guard warn instead of silently downgrading the file to legacy. Not currently reachable from `detect()` (it always writes a dict), but `materialize_section_details.py` (F9) is an unknown second writer.

7. **The `analysis` key name is generic for a file that `align_engine.py` treats as the arrangement's source of truth.** `detector` or `provenance` would be less likely to collide with a future field of the same name and would read better next to `signals.kick_presence_source`.

8. **`signals.kick_presence_source` already exists and records the real kick path** (`"kick-detector-v3"` vs `"stem-energy-threshold"`, line 1214). The new `analysis.kick_model` duplicates that fact in a second place with a weaker definition (it is `True` when a provider was merely *passed*, F8). Storing the existing `kick_source` string in `analysis` would be both more accurate and cheaper, and would let the hint path check the actual kick source rather than a boolean proxy. As written, `analysis.kick_model` can be `true` while the sections were in fact produced by the stem-energy threshold (a provider that was passed but whose branch fell through, or a future code path where the provider is None but the flag is set).

9. **The guard cannot fire from `--write-hints` (F4), so its warning is dead code in the documented workflow.** Only the `reverify_*` scripts (already known) reach it. This means the change's most reassuring console line never appears in the workflow the bug was found in, which may mislead a reader of the output into believing the file was protected.

10. **`detect()` does not report whether it actually wrote the json** (F3). It returns a result either way. A caller cannot tell "the json on disk is mine" from "the json on disk is still the old Phase 1a one that I was not allowed to touch". Adding a key to the returned result (for example `analysis.json_written`) would let `reverify_*` and any future caller notice, and it costs nothing.

11. **`validate_hints_vs_sections.py` reads the json's `bpm` for the hints-vs-sections gate but never reads `analysis.kick_model`.** Now that the json carries an explicit statement of which kick path produced the sections, the gate could report "this track's hints were compared against a kick-off analysis" and flag it. That would have surfaced F1 and F5 automatically on the first run against an existing project, instead of requiring this review to find them. Worth adding to the validator as a diagnostic, not as a failure.
