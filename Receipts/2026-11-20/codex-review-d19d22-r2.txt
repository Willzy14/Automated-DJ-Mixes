## FIX 3 - Publish and rollback

- **Interrupts.** `main` catches `BaseException`. When reconcile raises `KeyboardInterrupt` or `SystemExit` after `published = True`, rollback restores both files if the filesystem allows it. An interrupt after the final rename but before `compress_als` returns or `published` is set leaves the new ALS in place. A hard kill also leaves any already-published files visible.
- **Rollback can fail and discard the recovery copy.** If Windows denies the output replace or unlink, the shared `except OSError` skips report restoration too. `close()` then attempts to delete the output backup even though restoration failed. If report replacement fails, its restore `.partial` has no cleanup. A non-`OSError` raised during restore can mask the original failure.
- **Before publish.** An ordinary write failure before rename preserves the old ALS and normally cleans up the backup. Report restoration still runs and can overwrite another writer's report change even though this run never published. If `copy2` fails after creating a truncated backup, such as when the disk fills, `_PublishRollback.__init__` raises outside the `try/finally`. The prior output survives and the partial backup can remain.
- **Report identity.** Restoration compares bytes. If the report was deleted, `read_bytes()` raises and the report stays missing. Restoring changed bytes also gives the report a fresh mtime, which can affect the newest-report fallback. The normal CLI with a MixPlan supplies an explicit report path, so both paths agree while that file exists. If it disappears before reconcile, the fallback can validate against a different report beside the output. Rollback still targets the original report.
- **Concurrent writers.** Once `published` is set, restore acts on whatever is currently at `output_path`. It can overwrite or delete a later writer's valid ALS and revert that writer's report. The shared report `.tmp` adds another race: one writer can replace the report with the other writer's staged bytes.

Stage the ALS and the updated report, reconcile that exact pair, and publish only after the gate passes. The supplied `reconcile` reads and hashes its input paths, so it can use staged paths. Update the reported external test to assert that reconcile sees the intended bytes and that the final paths stay untouched until it passes. If concurrent runs must publish a consistent pair, serialize the final publication per destination. Two renames alone cannot commit the pair atomically.

## FIX 1 - Clip trim

- With both Current fields spelled `Value = "..."`, a 12-beat trim moves `Time` from 100 to 112 and `LoopStart` from 0 to 12, while `CurrentStart` stays at 100. With all four window fields split across lines, it changes only `Time`. The unreadable fields themselves stay untouched, but the clip is still edited blindly.

Read the actual clip elements and attributes, then patch the original text only after verifying all fields needed for the trim. Preserve the existing compatibility behavior for genuinely absent optional windows.

## FIX 2 - Partial files

The names end in `.partial`. A swallowed Windows `PermissionError` can leave a partial behind. None of the supplied production globs selects it as an ALS.

`token_hex(4)` gives a 32-bit random suffix, and both writers open the chosen name with `wb` without reserving it exclusively. In `apply_loops`, an interrupt after `stage_als` returns and before the caller enters its `try/finally` can also strand the stage.

## FIX 4 - Tail loops

Direct NaN and infinity inputs fail during `round()` or `int()`. Arithmetic can still produce infinity from finite inputs. On the four-bar loop fixture, `reps=10**308` returns an infinite target marker. `reps=1_000_000` returns bar `4000110`, and `partial_bars=5` is accepted for a four-bar loop. `int()` also silently truncates fractional counts. The later `validate_loop_spec` has repeat, partial-length, and extension limits, but `fills_from_decision` already returns the geometry and the planner uses its marker.

The builder is right about `ext <= 0`. After the earlier checks, either the repeat count and span are positive or the partial is positive, and neither term can be negative. The branch is unreachable and untested. Check the repeat count before coercion and enforce the existing geometry limits before returning the fill.
