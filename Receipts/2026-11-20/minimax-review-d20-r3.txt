## The defect: the new hint bound can refuse a correct real analysis

Round 3 added a bound that round 2 did not have. In `_check_cached_sections_inner` (lines 890-895):

```python
for key, val in hints.items():
    if not (isinstance(val, (int, float)) and math.isfinite(val)
            and 0 < val <= track_end + 0.01):
        return None, (f"{path.name} gives an invalid hint {key}={val!r} ...")
```

`track_end` is `max(end_sec)` over the sections, i.e. `n_bars * sec_per_bar` for a file `detect()` wrote. Three of the four `hints_from_stem_result` fallbacks are clamped to the track in effect, but **one is not**:

```python
if not first_break or first_break <= 0:
    first_break = first_drop + 16 * sec_per_bar
```

`first_break` is the only hint with no clamp against `end_sec`. So the bound is violated exactly when `first_drop + 16*sec_per_bar > track_end`.

**How short must a track be?** Two shapes, both real `detect()` outputs:

**(a) No "drop" section and no "break" section.** This is the shape `_assign_labels` produces when `first_drop is None` (no section satisfies `kf > 0.6 and bf > 0.5 and ef >= drop_thr`): every section becomes "intro" or "outro". It is also the shape the empty/partial kick readout produces. Then `first_drop` falls back to `16*sec_per_bar` and `first_break` falls back to `32*sec_per_bar`. The bound needs `32*sec_per_bar <= n_bars*sec_per_bar`, i.e.

**n_bars >= 32**, which is **60.0 s at 128 BPM, 61.0 s at 126 BPM, 64.0 s at 120 BPM, 54.9 s at 140 BPM, 44.1 s at 174 BPM.**

Worked example (128 BPM, `sec_per_bar` = 1.875, sections intro(0-16) + outro(16-32)): `first_drop` = 30.0, `first_break` = 60.0, `track_end` = 60.0, and `60.0 <= 60.01` passes. At 31 bars: `first_break` = 60.0 but `track_end` = 58.13, so `60.0 <= 58.14` is false and the track is refused. The exact cliff is 32 bars.

**(b) A real drop, but no "break" section, and the drop starts inside the final 16 bars.** Then `first_break = first_drop + 16*sec_per_bar` and the bound needs the first drop to begin at least 16 bars before the track ends. A 32-bar track that is 16 bars intro plus 16 bars drop passes exactly (30.0 and 60.0 against `track_end` 60.0); one bar shorter fails. `_assign_labels` explicitly supports tracks that end on a drop ("Never relabel a full DROP as outro"), so this shape is reachable.

**Why this matters more than a narrow edge case:** the write is all-or-nothing. One short track refusing means `exit 2`, no hints for any track in the project, and the existing `Hints/track_hints.json` left stale. A 60-second radio edit or a short-form asset in an otherwise fine project kills the whole run. The brief asks for exactly this ("a false refusal on a real short track or radio edit matters: say how short a track must be to hit it"), and the answer is 32 bars / about one minute.

The bound is also checking the wrong thing. The problem is not that the analysis is untrustworthy; it is that the *fallback* is arithmetic that is not clamped to the track. The fallback block's own comment says the fallbacks exist to "guarantee all four present + positive for the hint gate" - they were never clamped to the track length, and round 3 turned that gap into a refusal of a perfectly good analysis. The minimal fix is in `hints_from_stem_result`, not in the trust function:

```python
if not first_break or first_break <= 0:
    first_break = min(first_drop + 16 * sec_per_bar, end_sec)
```

or, equivalently, clamp all four hints to `end_sec` once at the end of the function. That keeps the round-3 guarantee (no hint past the end) while refusing nothing.

I am not asking for the fallback to be removed. Fabricating a hint is a separate (already accepted) problem; the point here is only that a *fabricated* hint must not cause a correct analysis to be refused.

## FOUND UNASKED

1. **The atomic write silently tightens the permissions on `Hints/track_hints.json`.** `tempfile.mkstemp` creates the file with mode 0600, and `os.replace` swaps the directory entry, so the new file is 0600 even when the file it replaces was 0644 (the old `Path.write_text` used the umask). Any consumer that reads the hints as a different user, or a CI step that collects the artifact as a different user, loses read access where it previously had it. `os.chmod(tmp, 0o666 & ~umask)` before the replace restores the old behaviour.

2. **`os.fdopen` failing leaks the descriptor and, on Windows, orphans the temp file.** If `os.fdopen(fd, "w", encoding="utf-8")` raises, the fd is never closed and the temp file is still open; `os.unlink(tmp)` then fails with `PermissionError` on Windows, and the `except OSError: pass` swallows it, leaving `.track_hints.*.tmp` behind. Exotic, but the same code path the round-3 author explicitly hardened.

3. **The `SECTIONS_STEM` json write in `detect()` is still not atomic.** `json_path.write_text(json.dumps(result, indent=1))` truncates then writes. A crash or a full disk mid-write leaves a truncated analysis file. That is pre-existing (main did the same) and not a round-3 regression, but round 3 made the hints write atomic and left the analysis write non-atomic, so the two are now asymmetric. A truncated analysis file is refused safely by the reader and overwritten safely by the guard, but `align_engine.py` globs `_Stem Analysis/SECTIONS_STEM_*.json` and would read it.

4. **The guard's refusal message is wrong for the empty-readout case, and `detect()` cannot tell its caller that nothing was written.** The message "this run has it off, so the file was NOT overwritten" is printed when the run had `--kick-model` **on** and the provider merely returned no readout (the `else` branch at line 1066). `detect()` returns `result` with `analysis.kick_model: false` in that case whether or not the write was permitted, so a caller holds in memory an analysis that is not the one on disk. A `result["analysis"]["json_written"]` flag would cost one line. (Minimax r2 raised the message; I am adding that the returned-result divergence is the part that can mislead an orchestrator.)

5. **`hints_from_stem_result` is called twice per track** - once inside `_check_cached_sections_inner` for the bound check and once in `main()` to build the hints. The checker's copy is discarded. It is deterministic today, but the two could drift, and returning the hints from the checker and reusing them removes the double call.

6. **The corpus has an orphaned analysis that the hints path cannot see.** `SECTIONS_STEM_Kyle Watson - The Afterhours (Extended Mix) 24 Bit MASTER.json` exists in `_Stem Analysis/` with a full kick-model analysis, but `Audio/` has no Kyle Watson wav in either proj or projB, so `--write-hints` (which globs `Audio/*.wav`) never reads it. `align_engine.py` globs `_Stem Analysis/SECTIONS_STEM_*.json`, so the arrangement phase sees 11 tracks where the hints file has 10. `validate_hints_vs_sections.py` only checks one direction of the mismatch (`set(hints_data) - matched_hint_keys`), so a sections track with no hint entry is silent.

7. **The bound closes the "out of range" half of the fallback problem but not the "fabricated" half.** A fallback hint that happens to land inside the track is indistinguishable from a real one for the trust function, yet `validate_hints_vs_sections.py` requires each hint to land within 8 bars of the corresponding ALS section, and a pure-arithmetic fallback will not. So a no-drop track can pass the round-3 bound and still fail the hints-vs-sections gate with a fabricated value. The round-3 bound is not a substitute for the accepted "fallbacks when a json has no drop or outro" item; it is an additional, orthogonal hazard.

8. **`_kick_provenance` is asymmetric about an unknown `kick_presence_source`.** `analysis.kick_model: true` plus an unrecognised source string is KICK_ON; no `analysis` key plus the same unrecognised source string is MALFORMED. Nothing in the tree writes such a string today, so this is latent only.

9. **The reader validates the analysis only through its own provenance label.** The trust function never checks that the `sections` in the file are consistent with the kick claim. A file whose `sections` were rewritten by another tool while `signals` or `analysis` were carried through keeps the label of the old sections. This is the same structural point minimax r2 made in its FOUND UNASKED item 1 and it is not addressed by round 3. I am not re-raising it as a verdict item because the brief records "no audio fingerprint or detector version in the json" as an accepted follow-up and the cheapest mitigation (refuse a json whose sections contain no "drop") was already proposed there; I am listing it only so the round-3 trust function is not later mistaken for more than it is.

10. **The `--track` validation only applies to `--write-hints`.** The `detect()` path still uses `audio / args.track` unvalidated, so `stem_detector.py <project> --track ../elsewhere.wav` runs `detect()` on a file outside `Audio/`. Pre-existing and outside the round-3 scope, but the asymmetry is now visible: the same argument is strictly validated on one path and not the other.
