## 2. Q1: what passes every usability check and is is still the wrong analysis to trust?

Two classes. The first is the serious one.

### 2a. A json whose sections contain no "drop" passes every check and three of its four hints are fabricated

`hints_from_stem_result()` never raises on a well-shaped json. It then fills any missing value from hard-coded fallbacks:

```python
if not first_drop or first_drop <= 0:
    first_drop = 16 * sec_per_bar
if not outro_start or outro_start <= 0:
    outro_start = max(first_drop + sec_per_bar, end_sec - 32 * sec_per_bar)
if not first_break or first_break <= 0:
    first_break = first_drop + 16 * sec_per_bar
if not last_bass_drop or last_bass_drop <= 0:
    last_bass_drop = max(first_drop, outro_start - 16 * sec_per_bar)
```

So a json whose `sections` contain only `intro` and `outro` entries - no `drop`, no `break`, no `fill` - passes every usability check and yields a `track_hints.json` in which `first_drop_sec`, `first_break_sec` and `last_bass_drop_sec` are **synthesised arithmetic, not derived from the analysis at all**. `first_drop_sec` would be `16 * sec_per_bar` (16 bars) for every such track regardless of the music.

Why that matters here specifically: this is exactly the shape the **pre-fix** build produces on the provider-empty path. In the r1 build (`review-d20/stem_detector.py`, lines 923-937) the model branch ran unconditionally:

```python
if kick_model or kick_provider is not None:
    _section_kick_on, _raw_kick_on = _model_kick_presence_per_beat(...)
    kick_on = _raw_kick_on          # fit() pads an empty readout to all-False
    kick_source = "kick-detector-v3"  # set regardless```

An empty provider readout is padded by `fit()` to `n_beats` all-False beats. `kick_on` is then all-False, so `kick_on_bar` is all-False, so in `_assign_labels` `kf` is 0.0 everywhere, `is_drop()` is never true, `first_drop` is `None`, and the label branch collapses to `label = "intro" if i < n/2 else "outro"`. The result is a two-section intro/outro json - and that json carries `signals.kick_presence_source: "kick-detector-v3"` (r1/main) or `analysis.kick_model: true` (r1).

**That is the answer to Q1 and to Q4: yes, a json can carry the kick-detector marker while its sections were not built from kick-detector data.** Round 2 fixed the *writer* (an empty readout now records `kick_model: false`), but the *reader* still trusts the marker the pre-fix writer stamped onto that exact degenerate file. `_check_cached_sections` checks a label next to the sections, never the sections themselves.

There is also a second, non-degenerate instance of the same class: **a json with no `signals` key at all.** `hints_from_stem_result` does `sig = res.get("signals", {})`, so an absent `signals` is `{}` and `.get("fills", [])` returns `[]` without raising. Such a json passes the hints-shape check (unlike `"signals": null`, which does raise and is refused). With `analysis.kick_model: true` it is accepted as fully verified, and `last_bass_drop_sec` falls back to `max(first_drop, outro_start - 16*sec_per_bar)` - fabricated.

Cheap fix, and safe on the real corpus: refuse a cached json whose sections contain no `"drop"` label. I checked all 11 real kick-on analyses under `d20-replay/proj/_Stem Analysis/` - every one contains at least one `"label": "drop"` (PAX, Offaiah, Ashibah, Ninetoes, Murphy's Law, Adam Ten, MASON, Kyle Watson, Darius, Eli Brown, Hannah Wants). A degenerate provider-empty analysis produces none, so this single check separates the good set from the bad set with no false positives on real data.

### 2b. A section time of `Infinity` yields a non-standard-JSON hints file

`math.isfinite` is applied to `bpm` only. Section times are not checked. `json.loads` accepts the literal `Infinity` by default, so a json containing `"start_sec": Infinity` parses fine, passes every check, and `hints_from_stem_result` returns `first_drop_sec: Infinity` (`not inf` is False and `inf <= 0` is False, so the fallback does not fire). `json.dumps` then emits `Infinity` into `track_hints.json`, which Python's `json.loads` accepts but which is **not valid JSON** per RFC 8259. Any strict downstream consumer (a browser `JSON.parse`, `jq`) breaks on it. Low severity, one-line fix (`math.isfinite` on the section times).

### 2c. Accepted and not re-raised

No audio fingerprint or detector version in the json (the brief's known item). A stale json from an older detector build with the same shape and a kick-on marker is still trusted. Same family as 2a but it needs the accepted follow-up, so I am not raising it as a new finding - I note it only because 2a's fix (checking the sections) also partly covers it.

## 3. Q2: any path where hints are written, or an existing hints file is modified or truncated, when a track was refused?

**In the check phase: no.** The `if bad: sys.exit(2)` is before `hints_dir.mkdir()` and before `out.write_text()`. There is no code path in which a refused track and a written hints file coexist. The `hints` dict built for the good tracks is simply discarded. The existing `Hints/track_hints.json` is not opened, not truncated, and not touched. `test_missing_cache_for_one_of_two_tracks_refuses_and_writes_nothing` asserts this by sha256 and it is a real assertion.

**In the write phase: yes, one window.** `Path.write_text()` opens with mode `"w"`, which truncates the existing file *before* writing the new content. If the write fails partway (disk full, an IO error, a `KeyboardInterrupt` between the truncate and the final flush), the pre-existing `Hints/track_hints.json` is left truncated or holding a partial JSON document. There is no temp-file-plus-`os.replace()`.

Note the ordering: `json.dumps(hints, indent=2)` is evaluated as the *argument* to `write_text`, so a serialisation failure would leave the file untouched. But the values are plain floats, so `dumps` cannot realistically fail. The exposure is the truncate-then-write window itself. The brief's "nothing written, an existing Hints/track_hints.json left byte-identical" promise is true for the refusal path and is **not** true for the success path under an IO failure. Severity: low (it needs an IO fault), but it is exactly the question asked.

Related, smaller: `hints_dir.mkdir(parents=True, exist_ok=True)` runs before the write and can itself raise (`PermissionError`), leaving no hints file at all and a traceback rather than the clean exit-2 message. Not a corruption, but the error surface is inconsistent with the refusal path.

## 4. Q3: does `--allow-unverified-cache` accept anything beyond missing provenance?

Covered in section 1. Summary: it accepts the missing-provenance case **and** the explicitly-negative-provenance case (`kick_model: false`, or `kick_presence_source == "stem-energy-threshold"`). ## 5. Q4: can a json carry "kick-detector-v3" while its sections were not built from kick-detector data?

**Yes.** Two independent ways, both live:

1. **The pre-fix provider-empty path**, exactly as the brief hypothesises. The r1/main code sets `kick_source = "kick-detector-v3"` unconditionally whenever `kick_model or kick_provider is not None`, while `fit()` pads an empty readout to an all-False beat array. The resulting sections are built from an all-kicks-off signal and carry the kick-detector marker. Round 2's reader accepts such a file as **fully verified, with no WARN** - via `analysis.kick_model is True` (r1 files) or via `signals.kick_presence_source == "kick-detector-v3"` (main-era files, which have no `analysis` key at all and therefore take the legacy branch).

   The legacy branch is exactly the hole: it was introduced to accept genuine main-era kick-model files, but the same marker was also written onto the degenerate provider-empty file. The two are indistinguishable by the marker.

2. **A later rewrite that preserves `signals`.** `signals.kick_presence_source` and `sections` are independent fields. Any tool that rewrites `sections` while carrying `signals` through produces a file whose provenance marker describes the *old* sections. `readers_of_sections_json.txt` shows `materialize_section_details.py:134` reading `SECTIONS_STEM_{clean_name}.json` and `:198` writing `SECTIONS_STEM_{clean_name}.json` into a `refined_stem_dir` - a second writer of the same filename shape. I cannot see its body, so I cannot confirm whether it preserves `signals` or `analysis`; that is the thing to check. If it preserves `signals` and drops `analysis`, a refined file lands on the legacy branch and is accepted as verified even though its `sections` were rewritten.

   Related, and this one is a false *refusal* rather than a false accept: `materialize_section_details.py` uses `clean_name`, not the raw stem. If `clean_name` differs from the wav stem in any way (trimmed, html-unescaped, stripped of a suffix), then either the filename no longer matches `SECTIONS_STEM_{w.stem}.json` (so `--write-hints` never sees it) or the `track` field inside it no longer equals `w.stem` (so it is refused). The `track` equality check protects against the refined file silently replacing the Phase1a file for the same track - that part is right - but it also means a cleaned-name refined file is unrefusable rather than merely refused.

The general shape of the defect: **provenance is a label stored beside the data, not a property of the data.** The check verifies the label and never the sections.

It is untested, and it is the single line that decides whether the json is marked verified. It is also testable without audio: extract the `if _model_used:` block into a helper, or pass `kick_provider=` into `detect()` with the envelope functions monkeypatched. As it stands, a mutation that sets `kick_model_used = True` unconditionally inside the model branch would leave the whole suite green.
- **"The energy-threshold presence is kept" on the empty-readout path.** `test_provider_returning_nothing_is_not_marked_used` only checks the returned flag. Nothing asserts that `detect()` keeps the energy-threshold `kick_on` (rather than the padded all-False array) when `used` is False. That is the behavioural half of the fix and it is untested.
- **The `else` branch's WARN text.** Untested.
- **Exit 2 on "no wav files".** Untested. The `if not wavs: bad.append(...)` line has no coverage.
- **More than one refused track.** The corpus requires "one `[REFUSED]` line each". The test has exactly one bad track, so the count-per-track behaviour is not pinned. A bug that emitted a single aggregated refusal line would pass.
- **`signals` absent entirely** (as opposed to `signals: null`). Untested, and it is the false-accept described in 2a.
- **The write itself.** No test asserts the file content when more than one track is written, that the key is `w.name` (with `.wav`), or that the written file is byte-stable.

## 8. Q7: anything in the non-hints paths that this round changed by accident?

Three real changes outside the hints path, none of them accidents in the "unintended" sense, but two are behaviour changes in the analysis path that deserve naming:

1. **`_model_kick_presence_per_beat` changed arity from 2-tuple to 3-tuple.** It is a private helper (leading underscore) and I found no caller outside `stem_detector.py` in the files I can see - the visible tree has no `kick_model_adapter.py`, no `orchestrator.py`, no `reverify_*.py`, so I cannot rule out a caller in the full repo. If any other module or test unpacks the old two-value form, it now raises `ValueError: not enough values to unpack`. This is a breaking signature change on a helper that was previously stable.

2. **The empty-readout behaviour change in `detect()`.** Pre-fix, a kick-model run with an empty provider readout produced an all-kicks-off analysis and labelled the file `kick-detector-v3`. Now it produces the energy-threshold analysis and labels the file `stem-energy-threshold`. This is the intended fix, and it is a real change to the analysis path - the sections for such a track will differ from the pre-fix build's. Worth stating explicitly because it means a re-run of Phase 1a on a project where the provider ever returned nothing will produce different sections than the file currently on disk.

3. **The overwrite guard now sees `kick_model_used` rather than "did the user pass `--kick-model`".** A kick-model run whose provider returns nothing is now refused permission to overwrite an existing kick-on json (message: "this run has it off"). The outcome is right; the wording is wrong.

4. **Cosmetic / non-behavioural:** `import math` and `import sys` added; the `--write-hints` and `--kick-model` help strings changed (the em dash in the `--write-hints` help became a hyphen, which is good for the ASCII rule); the two guard `print` calls gained `_ascii()`; `sys.exit(2)` introduced. No other non-hints line changed - I diffed the r1 file (`review-d20/stem_detector.py`) against the r2 file for the `detect()` body and the only differences are the three items above plus the `analysis` key that r1 already added.

5. **New stdout noise in the analysis path.** The `else` branch prints a WARN from inside `detect()`. In a non-hints run (`stem_detector.py <project> --kick-model`), that WARN is interleaved with the normal per-track summary lines. Cosmetic.

## 9. The brief's two open questions

**"Does exiting 2 on 'no wav files' break an existing caller or test?"**

Behaviour change, confirmed by reading both builds:

- r1: `wavs = []` -> the loop body never runs -> `hints = {}` -> `Hints/track_hints.json` is written containing `{}` -> exit 0.
- r2: `wavs = []` -> `bad` gets "no wav files found in <Audio>" -> exit 2, nothing written.

So yes, exit status changes from 0 to 2 for that input, and a previously-created `Hints/track_hints.json` is no longer overwritten with `{}`. I cannot check the caller: `orchestrator.py` is not in this snapshot and not in the visible tree, so I cannot say whether it uses `check=True` or inspects the exit code. Two things to note for whoever does check it:

- The r1 behaviour was worse in substance (it silently replaced a good hints file with `{}`), so refusing is the right direction. But it is a contract change that a caller running `check=True` will now surface as a hard failure on a project with an empty `Audio/` directory - for example a project that has not had its audio staged yet, or a smoke test that runs the step before staging.
- No existing test covers it: `test_missing_cache_for_one_of_two_tracks_refuses_and_writes_nothing` always has at least one wav. There is no test for the empty-project case, so the exit-2 contract is unpinned in either direction.

**"Does `track` equality fail for names with characters that another tool html-unescapes?"**

**No, and this is a non-issue for this check.** The comparison is `res.get("track") != wav_stem`, and both sides come from the same filesystem name:

- `wav_stem` is `Path("Audio/.../T.wav").stem`, i.e. the literal on-disk filename.
- `res["track"]` is written by `detect()` as `wav.stem` - the same literal on-disk filename.

The html-unescape lives in a different file and a different data path: `validate_hints_vs_sections.py` does `track_name = html.unescape(raw_track_name)` on the **ALS-derived `Sections_V<N>.json` keys**, because those keys come from ALS XML where `&` arrives as `&amp;`. The `SECTIONS_STEM_*.json` `track` field never goes through XML, so it holds the raw `&`.

I verified this on the real data: `d20-replay/proj/Audio/Adam Ten & Rafael - Call 911 24 Bit MASTER.wav` and the corresponding `SECTIONS_STEM_Adam Ten & Rafael - Call 911 24 Bit MASTER.json` both carry a literal `&` in the `track` field, and the REPLAY_A log shows that track passing the check and producing hints. So the equality holds for `&` names.

The residual risk is on the *other* side of the comparison: a file produced by a tool that cleans the name (`materialize_section_details.py` uses `clean_name`) would have a `track` field that does not equal the wav stem, and would be **refused**. That is a false refusal, not a false accept, and it fails safe. The reverse false accept - a file whose `track` matches but whose sections are for different audio - is not detectable without an audio fingerprint (the accepted follow-up).

## FOUND UNASKED

1. **The provenance check validates a label, never the data it labels.** This is the root of finding 2a and 2. `_check_cached_sections` reads `analysis.kick_model` or `signals.kick_presence_source` and stops there. It never asks whether the `sections` in the same file are consistent with that claim. The cheapest fix that closes the concrete hole: refuse a cached json whose `sections` contain no `"label": "drop"` entry. Verified against all 11 real kick-on analyses in `d20-replay/proj/_Stem Analysis/` - every one has at least one drop, and the degenerate provider-empty analysis has none. That single check also refuses the "no signals key" variant and most stale-detector variants for free.

2. **The pre-fix degenerate file is trusted as fully verified, with no WARN.** A file written by the r1/main build on the provider-empty path carries `analysis.kick_model: true` (r1) or `signals.kick_presence_source: "kick-detector-v3"` (main), and its sections are intro/outro only. Round 2 accepts it silently as the most-trusted category. This is the exact scenario Q4 asks about, and it is live. The reader-side counterpart of the writer-side fix is missing.

3. **`Hints/track_hints.json` is written non-atomically.** `Path.write_text()` truncates before writing. An IO failure between the truncate and the flush leaves the previous hints file truncated or holding invalid JSON, with no backup. Write to a sibling temp file and `os.replace()` it. The refusal path is clean; the success path is not.

4. **`math.isfinite` is applied to `bpm` but not to section times.** A section with `"start_sec": Infinity` passes every check and produces `first_drop_sec: Infinity` in the hints file - accepted by Python's `json.loads`, rejected by `JSON.parse` and by `jq`. The hints file stops being valid JSON.

5. **`bpm` NaN and `bpm` as a JSON boolean are implemented but untested.** The brief's own corpus lists NaN; `BAD_SHAPES` omits it. `isinstance(bpm, bool)` is likewise untested, so `bpm: true` slipping through as `1` would not be caught by the suite. Both are one-line additions to `BAD_SHAPES`.

6. **`hints_from_stem_result` is called twice per track** - once inside `_check_cached_sections` as the shape check (result discarded) and once in `main()` to build the hints. Harmless today (the function is deterministic and nothing mutates `res` in between), but it means the shape check is a smoke test rather than the thing that gates the write. Returning the hints from the check and reusing them removes the double call and the possibility of the two drifting apart.

7. **The `analysis` key spelling inconsistency bites in one direction.** `"analysis": null` takes the legacy branch and is judged on `signals.kick_presence_source`; `"analysis": {}` is judged as "present but not kick-on" and the legacy path is not consulted. The `is not None` test conflates "key absent" with "value null". Fail-safe today, but a deliberate distinction would be clearer, and the round-1 reviewers already flagged that `prior.get("analysis") or {}` in the guard silently downgrades a malformed `analysis` to "legacy, overwrite me".

8. **The guard's refusal message is wrong for the new empty-readout case.** "this run has it off, so the file was NOT overwritten" is printed when the run had `--kick-model` **on** and the model produced nothing. Same refusal, better outcome than r1, misleading explanation.

9. **`detect()` still cannot tell its caller whether it actually wrote the json.** It returns `result` whether or not `_may_overwrite_sections_json` permitted the write. Round 2 widens the set of runs where the file on disk and the returned result disagree (any kick-model run whose provider returned nothing). A `result["analysis"]["json_written"]` flag would cost one line and would let `reverify_*.py` and any future caller notice.

10. **The `REPLAY_A` / `REPLAY_B` logs cover 10 tracks; the `_Stem Analysis` folder holds 11.** `d20-replay/proj/_Stem Analysis/` contains a `SECTIONS_STEM_Kyle Watson - The Afterhours (Extended Mix) 24 Bit MASTER.json` and a matching `DETECT_*.png`, but `d20-replay/proj/Audio/` has no Kyle Watson wav. So that json is orphaned relative to the Audio folder, and both replays ignore it because the glob is over `Audio/*.wav`. Harmless for this change, but it means the replay evidence covers 10 of the 11 analyses actually present, and the orphaned file is a good illustration of the missing-audio-fingerprint item: nothing in the system can tell that json has no audio behind it.

11. **`analysis.kick_model` duplicates `signals.kick_presence_source` in a second place.** Round 2 has now made the two agree, which is good, but the boolean is the weaker of the two: it cannot express "the model ran and reported all-kicks-off" versus "the model ran and reported a real pattern", and it cannot distinguish a model that failed from one that legitimately found nothing. Storing the source string in `analysis` (or replacing the boolean with it) would make the reader's job a cross-check rather than a trust, which is the structural fix for finding 1.
