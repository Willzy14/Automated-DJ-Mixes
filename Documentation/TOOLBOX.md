### `Tools/plan_mix_decisions.py` (2026-11-20, Codex)

The planner publishes decisions with a same-directory atomic rename. Phase 2 verifies exact exit bars against the ALS clip and warp geometry with a one-beat detector tolerance. Use `--decisions-drop-rejected-loops` with `--decisions` to remove repeats rejected by the production loop-quality gate. Each drop and any resulting entry or exit change appears in the arrangement report. The original proposal stays on disk.

Reads a project's groove section JSONs and cached stem envelopes, then writes one top-ranked phrase-blend decision per adjacent pair. Pass `--sections` to use the same layout JSON as Phase 2, `--out` for the decisions, and optionally `--content` for the measured per-bar kick, bass, and music flags. The decisions add `out_end_bar` and optional `intro_loop` to name an exact outgoing stop and an incoming phrase repeat for `propose_arrangement.py --decisions`. The normal loop and ALS validators check the resulting geometry.

The standalone command requires a decision for every pair by default. `--allow-partial` lists unplanned pairs in `fallback_pairs` and leaves those pairs to the rule-based arranger. At least one pair must plan, and invalid inputs stop the command.

Whole bars only (2026-11-24, Claude Sonnet 5.5): when a pair's top plan has a fractional bar (for example a swap lined up on a fill end half a bar in), the planner never rounds it. It uses the cheapest of the planner's alternatives, then of its ranked candidates, whose decision passes the normal checks, and only then leaves the pair to the rule-based arranger. The log line, the decision's `reason`, an `n pairs used a whole-bar alternative` summary line, and the `whole_bar_alternative_count` and `whole_bar_alternatives` keys in the decisions JSON all show the pair and its cost difference to the top pick. Whole-bar mixes write byte-identical files.
### Phrase blend planner (2026-11-20, Codex)

- `Source/phrase_blend.py` ranks cue-based blends and accepts a fractional audio endpoint in `end_bar`. Pass `why=reasons` to `plan_blend` to collect input warnings and the reason for a `None` result.
- `Tools/score_blends.py` replays the seven owner placements and measures the effects of removing the bottom-end cost and the measured content.
- `Tools/score_tweak.py` (library `Source/tweak_replay.py`) decodes the planner's own set and the owner's hand-tweaked copy into planner terms, refuses to score unless the decoder reproduces the planner's own plan to within one beat, then reports where each tweaked blend sits among the planner's candidates (top, alternative, rank N of M, or outside the vocabulary and why), term by term, beside a trivial 16-in-16-out baseline. Added by: Claude (Sonnet 5.5), 2026-11-24.
- `Tools/blend_candidates.py` shows the ranked plans and reports why the planner found no admissible placement.

### `Tools/playlist_builder.py` (2026-10-06, Claude)
Builds a mix playlist from the Neon credits ledger via the read-only role `mix_planner_ro` (URL: `MIX_PLANNER_RO_DATABASE_URL` in the GitHub-folder `Credentials/Credentials.txt`; or `--rows file.json` offline). `sql` prints the SELECT; `build` filters by label/artist/year/streams/heat, orders by a genre-heat arc (`rise|wave|flat`), presets `hits|cool|cult|any`, one row per VERSION, drops acapella/dub/instrumental/radio edits. Genre tags are drafts. `--resolve` prints the master WAV per pick via `resolve_masters.py` (`Tests/test_playlist_builder.py` covers it, with the Neon reader stubbed).
Since 2026-11-25 `build` prints a MANIFEST before the track rows (selection logic and the track rows are unchanged): `built N of M requested` plus the reason when short (pool too small, repeat rows of one version, max-per-artist, each named only when it is a real cause), the filters as given, rows fetched vs the pool after `prepare()` with the count dropped per reason, genre and era spread of the picks against the pool, the heat curve, repeats against earlier mixes, and the cached beat-grid verdict per pick. Repeats: an earlier mix is a folder with `Audio/*.wav` under `Test Project/`, `Listening Sets/`, the main checkout's `Test Project/` (when run from a worktree) or the scratch `Projects/` folder; `--mixes-dir` (a folder of mixes, or one mix; repeatable) and `$DJMIX_MIX_ROOTS` REPLACE those defaults. Match = same SET of artist names, same title, same version (a remix is never its original; extended/original/mix are not version markers). The line says how many mixes were read, how many were unreadable or empty, how many file names could not be parsed and any path not found, or `repeats: not checked`. Grid verdicts (`PASS`/`FAIL`/`unknown (no cached verdict)`) are read only from earlier runs: gate lines in `<mix>/*.txt`, `<mix>/*.log` and `<mix>/Output/*.{txt,log}` (labelled `cached`), then `<mix>/Hints/grid_overrides.json` as a fallback (labelled `override`). Only lines in the gate's own shape count (name field, then `R=.. ph=..` or `-`). The gate prints the whole file name with its `.wav`, so a name that does not end in `.wav` was cut at 54 chars: it counts only when exactly one known file starts with it and that file is not newer than the log. Newest file wins and a tie goes to the worse verdict; a newer override FAIL can lower a log PASS (as the real gate would) but an override never raises a verdict. No new detector; unknown is never a pass; a cached FAIL is named in the summary line. `--credible` is only a guard: it refuses `--preset any` (exit 2, also for `sql` and for bare `--credible`, since the default preset is any) and changes nothing else; `--credible --preset cool` picks exactly what `--preset cool` picks. `any` ranks by stream percentile across all genres, so use a real preset for a coherent set.

### `Source/validate_beatgrid.py` (2026-06-11, v2 same day; RB-library CLI removed 2026-08-20)
Hard-stop gate: does each track's beat grid sit ON its audio? Whole-track kick onsets (150Hz lowpass — not mel fmax, which produces empty filters), half-beat-circle phase concentration (R) folds house offbeat-bass stabs so locked grids read high regardless of bassline; mean full-circle phase catches grids whose tempo is right but markers sit between the kicks (the Todd case). Per-track +1% detuned twin acts as a known-bad control. Calibrated on 22 tracks (08.06.26 + 09.06.26) + 12 more (11.06.26). Wired into `--sections-layout`; `--allow-bad-grids` to override.

**v2 — MIK tiebreaker (11.06.26 run):** percussion-heavy genres (Latin house, gospel stabs) smear R below the absolute thresholds even on correct grids. `check_grid(..., independent_bpm, db_bpm)` + `verdict_from(..., tempo_confirmed)`: a track is rescued from the ambiguous band only when R≥0.20, ≥5× its detuned control, the grid is internally consistent (span vs RB DB ≤0.5%) AND MIK agrees with the grid span ≤0.2% AND the phase is clean. Never rescues noise-floor grids; never overrides a bad phase.

**Grid overrides** (`<project>/Hints/grid_overrides.json`, applied by the orchestrator before enrichment so warp/cuts/gate all see the corrected grid):
- `shift_ms` — phase slide (the Todd fix). Written by CLI `--write-override <substr>` (measures, composes with existing shifts).
- `replace_grid` — full constant-grid synthesis for unusable grids (first case: La Trumpter — internally inconsistent RB grid, true 126 BPM confirmed by MIK + Sam). `_fit_anchor` kick-fits the anchor (bar-phase inherited from the old grid's downbeat); `write_grid_replacement(project, wav, rb, true_bpm)` PROVES the fit with the gate before writing — a failing fit is refused.

Library: `check_grid`, `enforce_beatgrid_quality`, `load_grid_overrides`, `apply_grid_override`, `write_grid_replacement`, `_fit_anchor`, `verdict_from` (pure). The Rekordbox-library CLI mode (`--write-override` against the RB library, incl. `write_phase_override`) was removed with the Rekordbox removal (2026-08-20); running the script now prints a retirement message. The live gate functions are unchanged.

### `Source/automated_dj_mixes/sequencer.py`

### `Source/kick_alignment_check.py` and `Tools/check_kick_alignment.py`
Added by: Claude (Sonnet 5.5) lead, Sonnet subagent build, MiniMax and Opus-subagent reviews (2026-11-23). After a mix is built it checks, for every blend, whether the two kick drums land together: maps the overlap through each track's per-beat warp markers (extended past the end markers at the last tempo, as Live does), reads short windows, and measures the lag three ways (edge = leading edge of the click, click = cross-correlation above 150 Hz, main hit = steepest rise above 40 Hz; positive = incoming later). Verdict per blend: PASS, WARN, FAIL or CANNOT_JUDGE (under 16 shared kick beats), with flags (SLOW_ATTACK, SCATTER_*, MINORITY_FLAM, DRIFT_FLAM, EDGE_DISAGREES, OFF_GRID, ...). Writes one picture per blend under `Output/Kick Alignment/` (worst and typical beats, both kicks stacked, beat line). `Tools/run_mix_pipeline.sh` runs it after the final validate; mode `warn` by default, `KICK_ALIGNMENT_MODE=fail` stops the build on a FAIL. Each estimator is judged by its own figures (starting figures Sam set on 2026-11-24 from five listening comparisons): click WARN 2.5 ms, FAIL 5.0 ms; main hit WARN 8.0 ms, FAIL 14.0 ms; the edge is reported only and never decides a verdict; a scattered main hit no longer forces a WARN while the click is trusted (SCATTER_MAIN is still printed; a click median at 2.5 ms or more, or a main median at 8 ms or more, still gives a WARN), a scattered click always does; HALF_OFF: a trusted click half at 5 ms or more, short of the 8 ms DRIFT_FLAM figure, raises a PASS to WARN (a half is a median of 8 to 40 beats, not one noisy beat); LARGE_LAG_FEW_KICKS (a lag seen on too few kicks) fires at the estimator's FAIL figure, and the `drifts X to Y` text when the halves differ by more than it and the estimator is not scattered; SLOW_ATTACK (click vs main medians) and EDGE_DISAGREES (edge vs click) fire above 8.0 ms and only raise a PASS to WARN; MINORITY_FLAM and the half-blend DRIFT_FLAM count a click beat or half against `CLICK_BEAT_FLAM_MS` 8.0 ms (single beats are noisier than medians: the click's per-beat IQR measured 5.3 to 6.5 ms) and the main hit against its 14.0 ms fail figure; the picture's worst beats are ranked by lag over each estimator's own warn figure. Exit codes: 0 ok, 1 FAIL in fail mode, 2 could not run, 3 nothing judged. `Tests/test_kick_alignment_check.py` (160 tests). Mix command step 3b+ says to LOOK at the pictures.

**Known limits of the starting figures** (Claude Sonnet 5.5, 2026-11-24, after two reviews). The figures come from one mix (Tech House 2026, the Get Right / No Panties / Taste chain) and five listening comparisons, ten (click, main) median pairs in all, so they are starting figures, not calibrated ones. A click flam of 5.0 to 7.9 ms on up to a fifth of the beats is not counted by the minority rule (single beats are judged at 8 ms because the click's per-beat interquartile range measured 5.3 to 6.5 ms). A verdict within about 1 ms of a figure is not reliable: the check resolves 1 to 3 ms and a re-measure differs by 0.2 to 1.1 ms. `MAIN_FAIL_MS` 14 is an interpolation: no listened blend separates the main hit from the click between +7.3 (approved) and +16.5 (a flam Sam heard). The edge never decides, although an edge of +7.7 ms with the click at 0 passes. A bimodal click (40 percent of the beats at +7.5 ms, the rest at 0) has a median of 0 and passes; only a fifth of the beats at 8 ms or more is counted. A scattered estimator is corroborated by the OTHER estimator at its own WARN figure, so a click median of 2.5 ms is a weak witness for a scattered main hit at 14 ms or more (click 2.4: WARN, 2.5: FAIL). A scattered main hit (IQR about 22 ms on No Panties) is not a reason to withhold a PASS when the click is clean; it is still printed as SCATTER_MAIN with no spread figure in the line. Old against new verdicts on the other kick-check files on this machine: see the 2026-11-24 entry in `Documentation/AI_CONTEXT.md`.

### `Source/grid_phase_fix.py` and `Tools/fix_grid_phase.py`
Added by: Claude (Sonnet 5.5) lead, Sonnet subagent build (2026-11-23); fix rounds 1 and 2 the same day (two-stage solve, apply mode removed, reviewer findings). Does by itself the two moves Sam made by hand to clear the Get Right / No Panties / Taste flams on the Tech House 2026 mix: a DRIFT FIT per track (the leading-edge click offset on every kick beat the clips use, running median over plus or minus 48 beats then a 31-beat average, applied to each warp marker by its BeatTime) and a SLIDE per track from a two-stage linear program: stage 1 finds the best worst lag t* of the blends that need fixing (the blends that were fine are held to what they were plus 0.4 ms), stage 2 finds the least total slide that keeps every blend within max(t*, 1.5 ms) (1.5 ms is the kick check's resolution, so the last millisecond is not chased; ties go to the slide sitting on one, earlier track). It reads the kick check's per-beat click lags once and predicts every blend's lag after any set of corrections exactly additively (lag_k = L_k + s_k - s_k+1), so it never re-measures per candidate, and it checks the written file against that prediction (within 2.5 ms). A fit counts as drift when max(largest correction, high minus low) reaches 4 ms; a fit reaching 12 ms or swinging 14 ms is refused (starting figures); kicks 15 ms or more from the grid are dropped as outliers. Drift is corrected only on tracks in a blend whose median click lag is 4 ms or more (`NEEDS_FIX_MS`; or a half at the kick check's 8 ms click per-beat figure or more); only those tracks are measured (about 1m40 for the 9-track Tech House set, most of it the two kick checks); slides are limited to those tracks and their neighbours. A track that sits in any blend the check could not judge is not moved at all (named in the report); a track with fewer than one warp marker per 4 source beats may slide but is not drift-corrected; a mix whose judged blends are all under 4 ms (its own noise floor `NEEDS_FIX_MS`, not the kick check's 2.5 ms click warn figure) is copied byte for byte. The output is a NEW ALS made by a text patch of the `SecTime` of `WarpMarker` lines only (CRLF kept, input never touched, no exponent notation, no negative SecTime), then measured with the kick check; the result is refused (exit 4, kept as `<name> REFUSED.als`) if the patch changed nothing or disagrees with the XML about which track is which, any judged blend's worst click lag grew by more than 0.4 ms, a blend became FAIL and its worst click lag also grew by more than 0.4 ms (a FAIL figure crossed by measurement drift is not a worse blend), or the re-measure differs from the prediction. Blends whose half is still at 8 ms (the click per-beat figure) or more after the fix are listed as STILL FLAMMING and the run is reported as not fixed; edge or main hit getting worse by more than 4 ms is listed too (the solve aligns the click, as Sam's ear chose). `Tools/run_mix_pipeline.sh` runs it after the kick alignment hook as a SUGGESTION, even when the kick alignment is about to fail the build: it writes `Sections V<B> Phased.als` and `Output/Grid Phase/`, validates the phased file (deleting it if that fails) and never stops the build. `GRID_PHASE_MODE` is `off` (any case, skips it), `suggest` (default and anything unknown, including `Apply` or `APPLY`: the final stays `Sections V<B>.als`) or `apply` (exactly that spelling). **Apply mode (2026-11-24, Claude Sonnet 5.5 build):** whenever it writes a phased file the tool also writes `Output/Grid Phase/grid_phase.json` (schema `grid-phase/1`): sha256 of the input and of the phased file, the constants, and for every CHANGED track its name, its position in the file, its exact ORIGINAL (SecTime, BeatTime) markers and its largest shift; read back from the two files by `grid_phase_fix.build_record`, which refuses a phased file that differs from the original outside the WarpMarker lines, in any BeatTime or in the number of tracks, clips or markers. A refused, nothing-to-do or failed run writes no record and removes any stale one (the json copy of the report is now `grid_phase_report.json`). `Source/validate_mix_plan_als.py --grid-phase <record> --grid-phase-original <original ALS>` (both REQUIRED together) leaves the pinned contract alone and checks the record: the phased ALS sha256 must equal the record's and the original's the record's `original_als_sha256`; the two files, decompressed, must be identical (same line count, same text on every line) except the SecTime value of the WarpMarker lines inside `<WarpMarkers>` of the tracks the record lists, so nothing else in the set (a fade, a mixer value, a clip edge) can differ; for each recorded track the recorded ORIGINAL markers must hash to the plan's pinned `warp_grid_sha256`, marker count and `source_grid_bpm`; the ALS markers must then have the same count and identical BeatTimes, be strictly increasing in both, and the shift (phased minus original, in ms) must stay inside the tool's own envelope, hard-coded in the validator and never read from the record (its `tool`, `tool_version` and `constants` fields are informational and ignored): max |shift| 27 ms (`MAX_ABS_SHIFT_MS`, drift 12 plus slide 15), shift swing max minus min 14 ms (`MAX_SWING_SHIFT_MS`), at most 0.5 ms between neighbouring markers (`MAX_STEP_SHIFT_MS`: the tool averages over 31 beats a profile of at most 14 ms, so 14/31 per beat; measured on the tool's output: 0.022 ms real Tech House 2026, 0 real DFTD, 0.182 ms steepest synthetic fixture; a marker grid with a marker only every 4 beats and an abrupt drift could be refused, which fails closed), and the phased track's own tempo within 0.05 BPM of the pinned one; every clip of the track must carry the same list, and the record's own largest shift must match the ALS; a track not in the record must still match its pin exactly; a record entry for a track that is not in the plan or the ALS, at the wrong file position, or listed twice fails; two tracks of the mix with the same display name make a record entry ambiguous and fail with a message saying so; a missing, unreadable or malformed record is a `FAIL:` line (exit 1, also written as `{status: FAIL, error}` to `--output`), never a trace and never a pass. The record binds the exact gzip bytes of the phased file, so re-saving the phased set (in Live, or any re-gzip) invalidates the record by design. The PASS line and the output json carry `grid_phase: N tracks, max shift X ms`; without `--grid-phase` the validator is unchanged. `Tools/run_mix_pipeline.sh` in apply mode still reconciles the unphased original first; then, if the tool wrote a phased file and a record, validate_als passed the phased file with the same flags as the original (`--expected-tracks N --require-devices --arrangement-report`), `Output/MIX_PLAN_RECONCILIATION_PHASED.json` (written by the reconciliation with `--grid-phase` and `--grid-phase-original`, and required to hold a `grid_phase` section) passes and the tool's `Output/Grid Phase/grid_phase_report.json` can be read, the final is `Sections V<B> Phased.als` and the last line reads `DONE: final = Sections V<B> Phased.als (grid phase applied)`, with `; still flamming: T07` and `; edge or main hit worse: T02 edge` added for every blend the tool could not make clean (the tool only promises that no judged blend's worst click lag got worse; an edge or main hit may). Adoption renames the reconciliation of the original to `MIX_PLAN_RECONCILIATION_ORIGINAL.json` and writes the phased one as the canonical `MIX_PLAN_RECONCILIATION.json`, and the log prints `final ALS: <absolute path> sha256 <hash>`. The first step that fails keeps the original, renames nothing, keeps a failed phased reconciliation as `MIX_PLAN_RECONCILIATION_PHASED.FAILED.json` and says so: `DONE: final = Sections V<B>.als (grid phase NOT applied: <reason>)`, loudly, never failing the build. Every mode (off included) first removes the phased file, its REFUSED and partial copies, the record, the phased reconciliations and any `..._ORIGINAL.json` of an earlier build. Out of scope and true on main too: `plan_hash` is the plan's hash of itself, so whoever can edit the plan can re-sign it; the reconciliation proves the ALS matches the plan, not that the plan is the one the pipeline wrote. `Tests/test_grid_phase_apply.py` (98 tests: validator and record writer, forgery tests included). Exit codes: 0 ok or nothing to do, 2 could not run, 4 refused. `kick_alignment_check.analyse_window(..., edge_only=True)` gives the kick test and the click edge without the cross-correlation grid and the main hit. `Tests/test_grid_phase_fix.py` (124 tests, 8 of them for the record) and 65 hook tests in `Tests/test_run_mix_pipeline.py` (45 of them for apply mode).

### `Source/bounce_check.py` and `Tools/check_bounce.py`
Added by: Claude (Sonnet 5.5) lead, Sonnet subagent build (2026-11-24). Measures what the listener hears at every join on the BOUNCED WAV, which the kick check (source audio through the warp markers) cannot see. Joins come from `MIX_PLAN.json` plus `ARRANGEMENT_REPORT.json` beside the bounce (refused if they disagree), or from an ALS with `--als` (a hand-edited arrangement has no matching plan; the ALS joins were checked equal to the plan joins on the DFTD mix, beat and second). The bounce starts at arrangement beat 0; seconds come from the tempo envelope (`render_check.TempoMap`), checked against the bounce length (never shorter than the arrangement, tail under 30 s) and against the audio (kick grid offset). Windows per join: 20 s before, the overlap, 20 s after (a side stops at the neighbouring join; under 3 s is not measured). Measures: loudness step and blend peak in LU (BS.1770 K-weighting taken from pyloudnorm, streamed in 10 s blocks, tested against pyloudnorm's meter), six band levels and the worst band step, the 40-150 Hz level against the louder side with L/R correlation and the worst bar, side over mid above 150 Hz, and kick flam (template fit of each track's own kick learnt just outside the overlap, plus the literal second-attack test, both with control beats where one track plays). The flam step needs clean kicks outside the overlap and says not measurable when it has none, or when the templates would be learnt from the beats they are checked on, or when the control beats flam too; it cannot see a flam under 3 ms. One line per join, `bounce_check.json`, one picture per join; with a ranges file (`Config/bounce_check_ranges.json`, built by `--calibrate Config/bounce_check_calibration.json` from the joins of Sam's accepted mixes) each join is called `inside the observed range` or `outside by X`, never pass or fail from a limit nobody has set. Exit codes: 0 done (whatever it found), 2 could not run, 3 the map does not fit the bounce (the report and `ATTENTION.md` are still written). `Tests/test_bounce_check.py` (every measurement on a synthetic bounce with a known answer, mutants killed).
**Attention gate (added 2026-11-24, Claude Sonnet 5.5 lead, Sonnet subagent build).** Report only, never a build failure, but built so the AI that builds the mix acts on it: every completed run writes `ATTENTION.md` beside the pictures (the same text in the json under `attention`) and ends its stdout on one line, `BOUNCE CHECK: 2 of 8 joins need a look (J01, J06): see <path>` or `BOUNCE CHECK: no join needs a look`. A join needs a look only for a measure with a direct audible meaning outside Sam's accepted range by at least a margin (`bounce_check.ATTENTION_MARGINS`, starting figures Sam will set: loudness step and blend peak 1.0 LU, low-end level vs sides 3.0 dB, low-end correlation fall 0.05, width step 3.0 dB) or a kick flam SEEN. Per-band tonal steps (sub included), worst-bar levels and a flam that was too few beats, not discriminating or not measurable are information only. `ATTENTION.md` also names everything that means the numbers cannot be trusted, so a join never reads as clean when something was not checked: `START WARNING`, `bounce does not fit the arrangement`, `NOT MEASURED` (any attention measure that could not be computed for a join: silent or short window, mono side, a channel with no 40-150 Hz energy, a NaN), `WARNING` (any other per-join note, e.g. a kick grid offset over 40 ms), `NOT JUDGED` (no ranges file, or no entry for a measure), `THIN` (a range built from under 5 joins), `NOT RUN` (`--no-flam`), `FLAM NOT MEASURABLE` (no join had a judgeable flam; information, not a flag). The md, the json and the screen carry one ASCII text (accents drop to their letter, o-with-stroke to o). Once past argument parsing the file always exists: a check that could not run (bad `--range-group`, unreadable bounce, no fresh bounce) writes `bounce check did not run (reason): no measurements`, and the hook writes the same for a hard crash. **The usual command is `python Tools/check_bounce.py --project "<project path>"`**: it finds the final ALS in `<project>/Output` (the highest `Sections V<N>`, the Phased file only when its same-basename WAV is not older than it, else the plain one), uses the same-basename WAV only if it is not older than that ALS (a WAV rendered before the ALS was last written belongs to an earlier arrangement), and writes into `<project>/Output/Bounce Check`. A build writes a brand new final ALS, so nothing has been rendered from it yet: `Tools/run_mix_pipeline.sh` runs the check itself only when a bounce not older than the final ALS already sits beside it (same-basename rule, e.g. `Sections V9 Phased.wav`, `--als <final>`), never stops the build on a crash (`bounce check did not finish (status N): no measurements, ...`), and otherwise prints `bounce check: no fresh bounce beside the final yet ...` (or the `older than the ALS (stale), ignored` line) followed by the exact command above as the last hint before DONE. `BOUNCE_CHECK_MODE=off` (any case) skips it and prints no hint; a stale `Output/Bounce Check/ATTENTION.md` is removed at the start of every build. A rebuild removes only the phased ALS, its REFUSED copy and `.partial` files, never a rendered bounce. Hook tests in `Tests/test_run_mix_pipeline.py`, including three that run the real tool.

## Added 2026-08-28

| Module | Purpose |
| --- | --- |
| `Source/mix_predict.py` | **Predicts a bounce's per-band level from SOURCE audio + the .als, with no render.** Per-band power = sum over tracks of `(master*trim)^2 * gain(t)^2 * band_power(source, low-shelf APPLIED AS A FILTER)`, source instant via the clip's own warp markers. The gate stays the authority on what a render actually contains; this answers "what would happen if" before anything is exported. REFUSES rather than approximating when the path is not the linear one it models: a non-empty master chain, an automated AutoFilter, or filter resonance. Static filters are modelled instead. Calibrated per band against the real V16 bounce (sub 0.46 dB MAE, bass 0.31, lowmid 0.31, mid 0.19, high 0.25); `can_size_correction(band, dB)` asks whether a move beats the band's p95 error rather than whether a band is accurate in the abstract. **Caveat: the low-band calibration comes from ONE mix and its mechanism is unexplained — re-measure on a second bounce.** Added by: Claude. |
| `Source/bass_residual.py` | **Sizes Sam's "option 2": how much of the OUTGOING's bass to leave in across a swap so the mix does not feel hollow, measured feed-forward with no render.** The quantity is the change the LISTENER hears across the swap - `out_unity+in_kill` before vs `out_kill+in_unity` after - not "outgoing minus incoming", which is a property of two records. Sizes by SEARCH over the shelf ladder (the shelf is a filter straddling sub and bass, so the dB it buys is not a closed form), capped at **Sam's ear-set -9.5 dB** (`RESIDUAL_CEILING` 0.335, a LISTENING ruling refined 2026-09-01 from the -5.68 launch value he called "clashy" - the residual keeps the WEIGHT, never the bass line; pinned by test). A clean run to the cap fires on his verdict even when predicted recovery is small; a guard-stopped run still demands recovery beat the model error. Returns a `ResidualDecision` for EVERY pair including refusals, so a build log can be read. Consumed by `apply_automation` behind `BASS_RESIDUAL_ENABLED`, **default OFF**. Guards: an ABSOLUTE overshoot bound vs the pre-swap level evaluated at 5 probes across the taper; refuses QUICK_SWAP (its Utility Gain is zero at the swap, so a residual would be inaudible); takes the LUFS levelling trims the mix ships with, not the arranged set's 0 dB faders. **Caveat: the firing gate borrows `BAND_P95_DB`, which was measured on SUMMED predictions, while what is gated is a difference of two per-track SHARES - errors that cancel in a sum can add in a difference. Widened by sqrt(2) as a stand-in; clearing it needs held-out solo renders from a second mix.** Added by: Claude. |
