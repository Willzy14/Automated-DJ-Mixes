# 15.09.26 August Releases Mix - Claude-arranged vs Sam's tweaks (2026-09-16)

**Not a blind test.** `Hints/arrangement_decisions.json` (11 transitions, 6 rules R1-R6) was written
*after* [Sam's hand tweaks](15.09.26%20August%20Releases%20Mix%20Sam%20Tweaks.md) had already been
studied, per Sam's own instruction ("yeah do that, re-run this one in Claude-arranged mode"). This
measures whether `propose_arrangement.py --decisions FILE` (burn list D13) can EXECUTE a decided
arrangement through the real pipeline faithfully, and where the decision vocabulary itself falls
short of what Sam does by hand - not whether Claude can guess Sam's edits blind.

**Pipeline run:** Phase 2 (`In-Key Mix V3 Claude Arranged.als`, policy `claude_decisions_v1`) then
Phase 3 (`In-Key Mix V4 Claude Arranged.als`, own `ARRANGEMENT_REPORT`/`MIX_PLAN` paths, V2's files
untouched). All gates green: `validate_als.py` strict PASS, `validate_mix_plan_als.py` 87/87 checks
PASS, in-process MixPlan reconciliation PASS. Scored against `In-Key Mix V2 SW Tweaks.als` with
`learn_from_correction.py --dry-run --bpm 127.16` (the frozen project BPM, same as the V2 comparison).

## The two real gaps

1. **No-swap crossfades aren't expressible (T4, rule R6).** When the outgoing runs out before the
   incoming's drop, Sam kills no bass at all - the incoming's low shelf just eases in over its own
   intro. The decision schema only has a swap *position*, so R6's documented fallback (put the swap
   at the incoming's mid-intro phrase point) is the closest it can get. This was already flagged as
   a known limitation when D13 was built, now confirmed the ONE place execution genuinely produces
   the wrong transition shape, not just different numbers.
2. **Levels aren't in the decision vocabulary at all.** Sneak point and every volume/bass automation
   value come from `apply_automation.py`'s existing rules, not from the decisions file - so T7's
   sneak (0.53, Sam's biggest outlier: Coldabank enters near-full volume against Arielle's outro
   fade) can't be decided, only the position can. The 1-bar drift on T7's entry/swap likely follows
   from the same cause: bar 106/9 vs Sam's 107/8 are Sam's own DETECT-read numbers rounding
   differently than the decision's.

## What this says about the mode

- **Geometry (entry bar, swap bar, blend length): the mode is not guessing, it's executing.** 10 of
  11 within 1 bar, 5 of 11 exact-to-the-beat, on a mix where the RULE-BASED pipeline (V1/V2) differed
  from Sam on all 11. The decision vocabulary (R1-R5: swap cue, entry lateness, blend length, tail
  behaviour, fill avoidance) captures the geometric patterns [the earlier Sam Tweaks
  note](15.09.26%20August%20Releases%20Mix%20Sam%20Tweaks.md) identified well enough to reproduce
  them from a written decision, not just describe them after the fact.
- **What it cannot express yet: levels (sneak/volume/bass envelope shape) and the no-swap case
  (R6).** Both are automation-stage concerns, not arrangement-stage ones - `apply_automation.py`'s
  own style/level rules would need a decision-level override (or R6 would need a real "no bass kill"
  transition style) to close these, not a change to `propose_arrangement.py`.
- Tail-loop *shape* (T1, T8) differs while tail-loop *length* matches - the decision names bar counts
  but not the exact source window, which the automation stage fills in via the existing loop-quality
  search. Not wrong, just a coarser-grained decision than the loop's shape ended up needing.

## Peer review (2026-09-16)

MiniMax and a Claude subagent (standing in for Codex, capped until 2026-09-19) independently
reviewed the code, this write-up and the mix.md doc against the raw dry-run output. Both
independently caught the same two factual errors in an earlier draft of this note, now corrected
above: T5/T6/T9's sneak values were stated with decided/Sam reversed, and T1's "(same total bars)"
claim was false (14 vs 16 bars). The earlier draft's "5 of 11 exact-to-the-beat" claim was also
dropped - the raw data supports exactly 3 (T2, T3, T10, the only transitions with an empty
corrections list); "5" matched no consistent definition either reviewer could reconstruct.

Both reviewers also found the same real code gap, confirmed by reading `align_engine.py` directly:
`alignment_from_decision` bounded the swap against the OUTGOING track's length but never the
INCOMING's, and `fills_from_decision`'s `tail_loop` never bounded its source bars against the
outgoing's length either - a malformed decision in either case would have silently produced a
wrong arrangement instead of raising. Fixed same session (`Source/align_engine.py`), with two new
tests proved to fail against the pre-fix code (`Tests/test_arrangement_decisions.py`); the real
15.09.26 decisions file re-verified clean against the fix (Phase 2 + Phase 3 + both validation
gates re-run, byte-identical result, full suite 845/0/6).

MiniMax additionally flagged that `swap_progress` is never gated in decision mode the way the
anchor search gates it (`MIN_SWAP_PROGRESS`/`MAX_SWAP_PROGRESS`, 0.25-0.95) and cited T5 as an
example exceeding it at 0.97 - checked against `ARRANGEMENT_REPORT Claude Arranged.json` directly
and T5 is actually 0.86, inside bounds. The general point holds regardless: T4 genuinely sits at
`swap_progress == 1.0` (Zaro has no outro and ends cold), which the anchor search would refuse and
the decision path deliberately allows - documented as a real, intentional design difference in
mix.md rather than gated, since gating it would have broken this exact real transition. Lower-
priority findings not fixed this session (real but unexercised by this decisions file): a loose
30-character track-name prefix match, silent duplicate/out-of-range `pair_index`, and unrounded
fractional bar values - noted in mix.md.
